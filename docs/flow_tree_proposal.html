Flow Draft Trees — where a flow matcher structurally beats EAGLE

Our flow drafters plateau at ~2.9 accepted tokens because a single chain commits to one token per position, and deep positions are uncertain. But a flow matcher outputs the full per-position distribution for all K positions in ONE parallel pass — exactly the input a draft tree needs. EAGLE must run K sequential passes to grow a tree; a flow gets it free. This is the one axis where flow's parallelism is an advantage, not a liability (cf. DDTree, which builds trees from one block-diffusion pass and lifts DFlash 5.5×→7.5×).

The idea, in one figure

Today — V6 chain

One parallel flow pass → per-position distributions → take the argmax at each position → a single length-4 chain → verify. A wrong token anywhere truncates the rest.

Proposed — V6 flow tree

SAME frozen V6 pass. At each position, keep the top-b candidates (they're already in the distribution), expand a small tree, verify the whole tree in ONE backbone pass with a tree mask, accept the longest correct path. A wrong argmax is recovered by a sibling.

Why this is grounded, not a guess

The tree's acceptance ceiling is directly computable from metrics V6's eval already logged — "is the true token in the drafter's top-b?" (token.top{b}_contains@i). If the true token is in the top-b at each position, a tree of that width covers it. Cumulative accepted-length = Σᵢ ∏j≤i P(true∈top-b at j):

The gain is largest on code (+0.9) — exactly the domain V6's chain was worst on, because the tree branches over precisely the uncertain deep positions where the chain truncates. A modest b=5 tree over V6's existing distributions exceeds EAGLE's chain on gsm8k, at no training cost. (These are upper bounds under greedy accept — real tree accept sits below the ceiling but well above the chain; this is the standard tree-vs-chain gap.)

The research question & plan

  1. Q: Does a flow matcher — which emits all K per-position distributions in one parallel pass — make a better/cheaper tree drafter than autoregressive EAGLE, which needs K sequential passes to grow the same tree?
  2. Build (inference-only, no retrain): a tree constructor that expands V6's top-b per position into a fixed-node-budget tree (DDTree-style: allocate nodes to high-probability paths), plus a tree-verification harness (tree attention mask over the draft nodes) that returns the longest correct path.
  3. Metric: report accepted-tokens/step (tree) vs V6 chain vs EAGLE chain, across gsm8k/stem/code/benchmark domains, sweeping node budget b∈{2,4,8,16} and tree depth.
  4. Systems note: tree attention masking is native on the 6 full-attention layers but needs recompute/state-fork on the 18 linear-attention layers — so live wall-clock on our hybrid backbone is gated by the deferred systems work (and by vLLM). Accepted-length is fully measurable now; it is the standard research metric and the honest deliverable.
  5. Optional lift: V6 was trained deterministic; a light retrain with noised init (like V8's) makes the flow a sampler, giving even more diverse tree candidates than top-b of a single distribution.

Why V6 is the right base: it is our best flow drafter (gsm8k 2.93 chain, first flow >1× live) and its Markov head sharpens exactly the per-position distributions a tree expands. The tree is a strict, orthogonal add-on: it multiplies acceptance by branching, on top of whatever the chain already achieves — and it is the single direction where a flow matcher has a structural edge over EAGLE, backed here by V6's own measured top-b coverage.
